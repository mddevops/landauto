# ADR-001 — Primary Identifier Strategy

**Status:** Accepted (owner, 2026-09-30) — Option B  
**Resolves:** D-085  
**Backlog:** X-007 (trigger: before P1-003)

## Context

- P1-003 (Workspace schema) is the first domain migration; every later schema task inherits the choice.
- Current keys are framework defaults: `users.id` bigint, `sessions.user_id` `foreignId`, `jobs` / `failed_jobs` bigint, `cache` string keys. No production data exists.
- Engines: development MySQL 8; PHPUnit and E2E SQLite; production engine not yet decided. The choice must behave identically on SQLite and MySQL (and PostgreSQL if chosen later).
- Security (SECURITY.md §8, TENANCY.md §76, PUBLISHING.md §94): knowing an ID must never grant access; public routes should not expose predictable internal IDs.
- Copy semantics (D-021, D-026) and future export/import copy object graphs.

## Options considered

- **A. bigint everywhere** — smallest keys; sequential IDs exposed in URLs / props.
- **B. bigint primary key + separate ULID `public_id` on externally addressed entities** — best storage / join performance with non-sequential external identifiers; two identifiers per exposed entity.
- **C. ULID primary keys** — one non-sequential identifier; larger keys and indexes.
- **D. UUID (v7) primary keys** — like C with longer `char(36)` storage.

## Decision — Option B

1. **Internal keys:** every table uses a `BIGINT UNSIGNED` auto-increment primary key (`$table->id()`); foreign keys are `BIGINT UNSIGNED` via `foreignId(...)->constrained()`. Framework tables keep their existing keys (`users.id` is already `BIGINT UNSIGNED`).
2. **Public identifier:** every entity addressed from outside the backend — in URLs, route parameters, Inertia props used as identifiers, API payloads, the public runtime or exports — has a `public_id` column: ULID, `$table->ulid('public_id')->unique()` (not nullable), generated by the model on create (`HasUlids` with `uniqueIds(): ['public_id']`, which keeps the integer primary key). `public_id` is **immutable**: assigned once at creation, never regenerated, reassigned or accepted from user input (not fillable). A copied entity (Template instantiation, D-021 / D-026 copies, import) is a new row with a new `public_id`. Expected examples: Workspace, Workspace Membership, Site, Page, Form, Submission, Asset, Integration, Workspace / Site Vehicle, Domain. Each schema task states whether its entity is externally addressed.
3. **Never expose numeric IDs of those entities:** route model binding uses `public_id` (`getRouteKeyName()`); Inertia props, API responses and exports are built explicitly and contain `public_id`, never the numeric `id` (nor numeric foreign keys of such entities); forms send `public_id`, and the backend resolves it within the current Workspace / Site scope.
4. **Internal-only tables** (technical pivots, logs, `user_auth_identities`, snapshots, queue data) get no `public_id`. Pure technical pivots may use a composite primary key of their foreign keys instead of `id()`. **Workspace Membership is not a technical pivot:** it is a first-class domain entity (role, status, timestamps; managed through UI / routes — change role, remove member) and therefore has its own `id()`, a `public_id`, and a unique (`workspace_id`, `user_id`) constraint.
5. **Users:** no `public_id` for now; the UI addresses people through memberships (which have `public_id`). Exposing `users.id` is avoided where not needed (shared-props allowlist in `X-011`). Adding `users.public_id` later is a small additive migration.
6. **Global catalog:** customer-facing and public URLs use slugs or `public_id` as the catalog tasks define; internal catalog joins use bigint IDs.
7. **Secrets are not IDs:** invitations, preview links, unsubscribe, webhook secrets and similar use separate random tokens (hashed where applicable). A `public_id` is non-sequential but not secret; every access is still authorized server-side through Workspace / Site ownership.
8. **Tests:** tenant-isolation / policy tests request another Workspace's resource by its real `public_id` and expect denial (403 / 404); a test per exposed entity confirms serialized props do not contain the internal `id`.

## Consequences

- Positive: compact integer keys and joins everywhere; non-sequential external identifiers; engine-neutral; Laravel-native (`HasUlids` + `uniqueIds()`).
- Negative: two identifiers per exposed entity; leaking `id` instead of `public_id` is a silent mistake, mitigated by explicit props / resources, `getRouteKeyName()` and the serialization tests above. Graph copies (Templates, D-021 / D-026) remap bigint IDs after insert and generate new `public_id`s.
- Convention recorded in rule `.cursor/rules/50-database.mdc` and DATABASE.md §2 / §95.
